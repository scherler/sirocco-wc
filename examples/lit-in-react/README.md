# Using a sirocco-wc Lit component from a React app

sirocco-wc scaffolds Lit web components for Jenkins-plugin consumption: one
bundled `dist/index.js` + `dist/index.css`, loaded from a Jelly page that has no
bundler at all. That is not the only way to consume them. This folder documents
and *proves* the other way — a React application importing a sirocco-wc-generated
Lit component as an ordinary ES module.

React's synthetic-DOM layer has historically fought custom elements (props vs.
attributes, no JSX syntax for custom events), and that story changed again with
React 19's native custom-element support. The four sections below cover what
actually breaks, what actually works, and which version boundary each behaviour
sits on. Everything here was verified against a real build, not written from
memory — see [Verified versions](#verified-versions).

> **Confidentiality note for anyone extending this example.** Keep it generic.
> Refer only to "a React app" / "a React host application". Do not name, hint at,
> or model the demo component on any specific internal or customer application,
> product, or team — not in code, not in comments, not in commit messages, not in
> the PR description. The demo component here is deliberately a meaningless
> `demo-greetingcard`.

## React version-dependent integration

### React 19+ — pass props directly (recommended)

React 19 added first-class custom-element support. For a tag React does not
recognise, it now checks whether a matching DOM *property* exists on the element
instance and assigns the JSX value to it; only if no such property exists does it
fall back to `setAttribute`. That means non-string values — arrays, objects,
functions, `Date`s — reach the component intact, with no serialisation:

```tsx
import 'lit-component/src/components/greetingcard'

export function Card() {
  return <demo-greetingcard name="World" items={['tea', 'coffee']} />
}
```

This is the whole integration. No wrapper, no ref, no `useEffect`. It is what
[`react-app/src/App.tsx`](./react-app/src/App.tsx) does, and it is the pattern to
reach for on any React 19 codebase.

Evaluated against the running page, this is what "property, not attribute"
actually means:

```js
const el = document.querySelector('demo-greetingcard')
Array.isArray(el.items)     // true
el.items                    // ['tea', 'coffee']  — the same array, not a copy of a string
el.getAttribute('items')    // null  ← no attribute was ever set
```

No attribute exists, so no serialisation and no reparse happened at all.

The one thing React 19 still does *not* give you is a JSX form for custom events
— there is no `onGreetingClicked` prop. Event listening stays imperative; see
[Custom events](#custom-events-no-jsx-form-on-any-react-version).

### Before React 19 — refs or `@lit/react`

Pre-19, React serialised every unrecognised-tag prop through
`setAttribute(name, String(value))`. `items={['tea', 'coffee']}` became the
attribute string `"tea,coffee"` — which is not JSON, so Lit's converter cannot
recover it (it lands as `null`, silently; see
[Complex props](#complex-props-arrays-and-objects)). Two fallbacks:

**Imperative property assignment via a ref.** Verbose but dependency-free:

```tsx
function Card() {
  const ref = useRef<HTMLElement & { items?: string[] }>(null)

  useEffect(() => {
    if (ref.current) ref.current.items = ['tea', 'coffee']
  }, [])

  return <demo-greetingcard ref={ref} name="World" />
}
```

**`@lit/react`'s `createComponent()`.** Generates a real React component that
maps props to properties and custom events to `on*` props, so consumers write
idiomatic JSX:

```tsx
import { createComponent } from '@lit/react'
import * as React from 'react'
import { Greetingcard } from 'lit-component/src/components/greetingcard'

export const GreetingCard = createComponent({
  react: React,
  tagName: 'demo-greetingcard',
  elementClass: Greetingcard,
  events: { onGreetingClicked: 'greeting-clicked' },
})
```

Treat both as **fallbacks for pre-19 codebases**, or for the narrow cases where
you want the event-as-prop ergonomics `createComponent` provides. On React 19
neither is needed to pass props, and adding `@lit/react` to a React 19 app just
to render one component is not worth the dependency.

## Prop and event boundary

### Simple props (strings, numbers, booleans)

These have always worked, on every React version, because a string attribute is
exactly what the DOM wants:

```tsx
<demo-greetingcard name="World" />
```

Lit's `@property({ type: String })` picks it up from the attribute. Numbers and
booleans go through Lit's converter (`Number(value)`, and "attribute present"
for `Boolean`), so `count="3"` arrives as the number `3`.

### Complex props (arrays and objects)

Three forms, and it is worth knowing exactly which one you are using.

**1. A real JS value as a JSX prop — recommended, React 19+.**

```tsx
<demo-greetingcard items={['tea', 'coffee']} />
```

Set as a DOM property. No string ever exists. This is the primary pattern.

**2. A literal JSON string attribute — works, but do not reach for it.**

```tsx
<demo-greetingcard items='["tea","coffee"]' />
```

This *does* work, and the reason is worth knowing: Lit's default converter's
`fromAttribute(value, type)` runs `JSON.parse(value)` when the declared `type` is
`Array` or `Object`. So a valid-JSON attribute string round-trips into a real
array. Two caveats make this a curiosity rather than a pattern:

- It does **not** apply if the property is declared `attribute: false`
  (property-only, no attribute reflection), or with a type Lit's converter does
  not JSON-decode, or with a custom `converter`. Then only forms 1 and 3 work.
- Lit deliberately **does not throw** on invalid JSON — it catches and assigns
  `null`. That is exactly why the pre-19 `"tea,coffee"` stringification fails
  *silently*: `JSON.parse("tea,coffee")` throws, so the property becomes `null`
  and you get an empty list with a clean console.

**3. Imperative assignment via a ref — the pre-19 fallback.**

```tsx
useEffect(() => {
  if (ref.current) ref.current.items = ['tea', 'coffee']
}, [])
```

Bypasses attributes entirely. Correct on any React version, required pre-19.

### Custom events: no JSX form on any React version

JSX has no `onGreetingClicked` prop — React only maps its own known event names.
Listening to a Lit `CustomEvent` means `addEventListener` on a ref, inside
`useEffect`, with cleanup:

```tsx
const cardRef = useRef<HTMLElement>(null)
const [lastGreeted, setLastGreeted] = useState<string | null>(null)

// Memoised on purpose — see below.
const handleGreetingClicked = useCallback((event: Event) => {
  const { name } = (event as CustomEvent<{ name: string }>).detail
  setLastGreeted(name)
}, [])

useEffect(() => {
  const el = cardRef.current
  if (!el) return

  el.addEventListener('greeting-clicked', handleGreetingClicked)
  return () => {
    el.removeEventListener('greeting-clicked', handleGreetingClicked)
  }
}, [handleGreetingClicked])
```

**The `useCallback` is load-bearing, not style.** `removeEventListener` only
detaches a listener when handed the *same function reference*
`addEventListener` received. An inline arrow is a fresh reference every render:
the `add` works, the `remove` silently no-ops, and every remount leaks a
listener — including React Strict Mode's deliberate mount/unmount/remount in
development, which will make the handler fire twice on the very first click.

On the Lit side, the event must escape the shadow root, which needs **both**
flags:

```ts
this.dispatchEvent(
  new CustomEvent('greeting-clicked', {
    detail: { name: this.name },
    bubbles: true,
    composed: true, // without this the event stops at the shadow boundary
  })
)
```

`bubbles: true` alone is not enough — `composed: true` is what lets it cross out
of the shadow tree into the host document where React's listener is attached.

## Shadow DOM style isolation

Every sirocco-wc component renders into a shadow root (Lit's default) and gets
its Tailwind output injected as `static styles`. The consequences for a React
host page:

- **The host page's global CSS does not reach inside the component.** A Tailwind
  preflight/reset, a global `button { … }`, a CSS-framework utility class — none
  of it applies to the component's internals. This is a feature: the component
  looks the same in every host.
- **The component's CSS does not leak out.** Each component's `.styles.ts` is
  compiled per-component (sirocco-wc points Tailwind's `content` at that one
  `.ts` file), so it contains only the utilities that component uses, scoped to
  its shadow root.
- **Selectors from outside stop at the boundary.** `document.querySelector('demo-greetingcard button')` finds nothing. You need `el.shadowRoot?.querySelector('button')`.

This PoC demonstrates it visibly rather than asserting it.
[`react-app/src/index.css`](./react-app/src/index.css) ends with bare `button`,
`ul`, `li` element rules — as global and unspecific as CSS gets — and `App.tsx`
renders the same `<ul><li>` markup twice, once in the host document and once
inside the component. In the browser: the host list is dashed, square-marked and
uppercase; the component's identical list is not. The page's only `<button>`
lives inside the shadow root and stays undashed.

Measured in the running page:

| | `ul` in host document | `ul` inside shadow root |
| --- | --- | --- |
| `border-style` | `dashed` | `none` |
| `list-style-type` | `square` | `disc` (UA default) |
| `li` `text-transform` | `uppercase` | `none` |

`document.querySelectorAll('demo-greetingcard button').length` is `0`.

### The two documented exceptions

1. **Inherited properties cross the boundary.** `color`, `font-family`,
   `line-height`, `letter-spacing` and friends inherit into a shadow tree as
   normal, because inheritance flows down the flattened tree. So the host page's
   base typography *does* affect the component unless the component overrides it.
2. **CSS custom properties cross the boundary, and `::part()` reaches in.**
   Custom properties inherit, which makes them the sanctioned theming channel:

   ```css
   /* host page */
   demo-greetingcard { --card-accent: #aa3bff; }
   ```
   ```css
   /* component's own CSS */
   :host { border-color: var(--card-accent, #ccc); }
   ```

   A component can additionally expose internals with `part="…"` and let the host
   style them via `demo-greetingcard::part(label) { … }`. Both are opt-in by the
   component author — a host cannot theme what the component did not expose.

## Distribution: npm package vs. dist bundle

sirocco-wc's generated projects build to a single bundle for Jenkins:

```jelly
<script type="module" src="${resURL}/plugin/$PLUGIN_NAME/js/index.js" />
<link rel="stylesheet" href="${resURL}/plugin/$PLUGIN_NAME/js/index.css" />
```

That pattern exists because a Jelly page has **no bundler**. It must be handed
one already-bundled file. A React app is the opposite situation: it *is* a
bundler pipeline.

### Recommended for a React consumer: the npm package path

Publish (or `file:`/workspace-link) the component package and import it:

```jsonc
// react-app/package.json
"dependencies": {
  "lit-component": "file:../lit-component"
}
```
```tsx
import 'lit-component/src/components/greetingcard'
```

Why this and not the bundle:

- The host's bundler resolves `node_modules` and tree-shakes ES modules, so a
  React app importing two of twenty components ships two.
- One copy of `lit` in the final graph. A prebuilt bundle carries its own copy of
  Lit, and loading it alongside a React app that also has Lit gives you two
  `ReactiveElement` registries and duplicate-`customElements.define` errors.
- Real module semantics: named exports, source maps to the component's own
  source, HMR during development, and type declarations if the package ships
  them.
- Version pinning and `npm audit` work normally.

### When the dist-bundle path is still right

- The consumer has no bundler (Jelly, a plain `<script>` tag in a static page,
  a CMS template) — the original sirocco-wc use case.
- You need the component available to pages you do not build, from a CDN or a
  plugin's static resource path.
- The consuming app is not JavaScript-first and you want one drop-in artifact
  and no dependency on the consumer's toolchain.

If you do load a bundle into a React page, load it exactly once (a plain
`<script type="module">` in `index.html`, not an `import` inside a component that
may render more than once) and do not also depend on the component package —
pick one path.

## Running the PoC

Two independent npm projects, in order. `react-app` depends on `lit-component`
through a `file:` link, so `lit-component` must be installed first.

```bash
cd examples/lit-in-react/lit-component
npm install
npm run css:build           # regenerates the gitignored Greetingcard.styles.ts

cd ../react-app
npm install
npm run build               # tsc -b && vite build — must pass with 0 errors
npm run dev                 # http://localhost:5173
```

In the browser you should see: `Hello, World` on a button, a list of `tea` /
`coffee` rendered *inside* the shadow root and therefore unstyled by the host's
global CSS, and — after clicking the button — `Last greeted: World` rendered by
React from the custom event's `detail`.

### `npm run css:build` is a required first step, not optional

`*.styles.ts` is gitignored repo-wide (`.gitignore` line 9), so
`Greetingcard.styles.ts` does **not** exist after `git clone`. It is generated
output. Skip the step and `react-app`'s build fails with an unambiguous
resolution error naming the missing file:

```
[UNRESOLVED_IMPORT] Could not resolve './Greetingcard.styles' in ../lit-component/src/components/greetingcard/index.ts
```

Run `npm run css:build` in `lit-component` and build again. Use `css:build`, not
`generate` — `generate` re-runs the scaffolder and would append a duplicate
`export * from './greetingcard/index';` line to `src/components/index.ts`.

### Why two package managers in one repo

The root sirocco-wc repo uses Yarn Berry with PnP (`.yarnrc.yml`, `.pnp.cjs`).
`lit-component` and `react-app` use plain npm with their own `node_modules` and
`package-lock.json`. This is intentional, not an oversight:

- It is the realistic consumer. A React app is not going to adopt Yarn Berry PnP
  in order to consume one web component.
- It keeps the PoC honest. `lit-component` gets the `sirocco-wc` CLI from the
  **published npm package** (`sirocco-wc@2.0.0-snap`, a `devDependency`), the
  same way any external consumer would — not from the repo's own `bin/`. Nothing
  here depends on the root repo being installed.
- The root `.gitignore` already ignores `node_modules` (line 8) and `dist`
  (line 6), so neither nested install tree nor build output reaches git.
  `.npmignore` excludes `examples` so none of this ships in the published
  `sirocco-wc` tarball.

The one thing pinned deliberately hard: `react-app/package.json` and
`lit-component/package.json` use **exact versions, no `^` or `~`**. The two
sharpest findings in this PoC (the decorator flags and the JSX augmentation
shape) are both version-sensitive, so a floating range could silently invalidate
the documentation.

## TypeScript setup, and two traps

### Legacy decorator flags belong in *both* tsconfigs

Lit's `@customElement`/`@property` are TypeScript legacy (experimental)
decorators, so both projects set:

```jsonc
"experimentalDecorators": true,
"useDefineForClassFields": false
```

Setting them only in `lit-component/tsconfig.json` is **not** enough. The Vite
scaffold's `npm run build` is `tsc -b && vite build`, and `tsc` type-checks one
whole program under one option set — it does *not* apply "nearest tsconfig per
file". `Greetingcard.ts` is pulled into `react-app`'s program transitively via
`App.tsx`'s import, so without the flags in
[`react-app/tsconfig.app.json`](./react-app/tsconfig.app.json) you get:

```
../lit-component/src/components/greetingcard/Greetingcard.ts(9,4): error TS1240: Unable to resolve signature of property decorator when called as an expression.
../lit-component/src/components/greetingcard/Greetingcard.ts(9,4): error TS1270: Decorator function return type 'ClassAccessorDecoratorResult<Greetingcard, string>' is not assignable to type 'void | ((this: Greetingcard, value: string) => string)'.
```

Without `experimentalDecorators`, TypeScript assumes standard (TC39 Stage 3)
decorators, whose *type* signature Lit's decorators do not satisfy in that
position. Note this is a **type-check-only** failure: a bare `vite build` or
`vite dev` — esbuild's isolated per-file transform, no type-checking — produces a
working bundle either way, because Lit's decorators handle both legacy and
standard call shapes at runtime. The flag exists to satisfy the `tsc` gate. The
scaffold's `erasableSyntaxOnly: true` does not conflict with either flag.

### JSX typing: `declare module 'react'`, not `declare global`

The custom element's tag is unknown to JSX, so it needs an `IntrinsicElements`
entry. The pattern most search results give you is wrong on current React:

```tsx
// ✗ Silently ignored under @types/react@19+.
declare global {
  namespace JSX {
    interface IntrinsicElements { 'demo-greetingcard': … }
  }
}
```

`@types/react@19` removed the global `JSX` namespace; `JSX` now lives nested
inside `declare namespace React`. There is nothing global left to merge into, so
the augmentation compiles fine, does nothing, and `tsc` still reports:

```
src/App.tsx(83,7): error TS2339: Property 'demo-greetingcard' does not exist on type 'JSX.IntrinsicElements'.
```

The form that works is a module augmentation of `react` itself:

```tsx
// ✓
type GreetingcardProps = DetailedHTMLProps<
  HTMLAttributes<HTMLElement>,
  HTMLElement
> & {
  name?: string
  items?: string[]
}

declare module 'react' {
  namespace JSX {
    interface IntrinsicElements {
      'demo-greetingcard': GreetingcardProps
    }
  }
}
```

Intersecting with `DetailedHTMLProps<HTMLAttributes<HTMLElement>, HTMLElement>`
is what makes `ref`, `className`, `style` and the standard DOM attributes
type-check on the tag; the extra members declare the component's own props.

## Known failure mode: the element never registers

The single most confusing custom-element failure for a React developer, because
there is no error of any kind.

**Symptom.** `<demo-greetingcard>` renders as an empty inline element. No text,
no list, no console warning, no React error. Any props you passed are sitting on
the element as expando properties, doing nothing.

**Cause.** `customElements.define()` never ran, so the browser treats the tag as
an unknown element — which is perfectly legal HTML, hence the silence. With Lit
that call is a *side effect* of `@customElement` at module evaluation time, so
it happens only if the component's module is actually imported and evaluated.
Usual reasons: the side-effect-only import was never added; an editor or linter
"unused import" cleanup removed it; a bundler tree-shook it because the package
is not marked side-effectful and nothing else references the module.

**How to confirm.** In devtools, either:

- Inspect the element — a registered custom element shows a `#shadow-root` child;
  an unregistered one has no children at all.
- Run `customElements.get('demo-greetingcard')` in the console. `undefined`
  confirms it.

**Fix.** Ensure the side-effect import runs, at a module that definitely
evaluates:

```tsx
import 'lit-component/src/components/greetingcard'
```

If a tree-shaking bundler is dropping it anyway, the component package is
claiming to be side-effect-free when it is not: make sure its `package.json`
does **not** carry a blanket `"sideEffects": false`, or import the class by name
and reference it so the module has a live binding.
