# `lit-component` — the generated Lit component

A standalone local package holding exactly one Lit component,
`<demo-greetingcard>`, generated by the real `sirocco-wc` CLI. The sibling
[`../react-app`](../react-app) consumes it through
`"lit-component": "file:../lit-component"`.

See [../README.md](../README.md) for the integration documentation. This file
covers only how the component here was produced, so it can be reproduced or
regenerated from scratch.

> Keep any extension of this example generic — see the confidentiality note in
> [../README.md](../README.md). `greetingcard` is a deliberately meaningless
> demo name.

## Why this is a real package

It would have been shorter to hand-write one `.ts` file. It is a package with its
own `package.json`, its own `lit` dependency, its own `tsconfig.json` and its own
`node_modules` because that is what makes the PoC prove anything:

- **It gets the CLI from the published npm package.** `sirocco-wc@2.0.0-snap` is
  a `devDependency` here, so generation runs the same published artifact an
  external consumer would install — not this repo's `bin/`. Nothing in
  `examples/` depends on the root repo being installed, or on Yarn/PnP.
- **It gives `react-app` something real to depend on.** A `file:` dependency, not
  a relative `../../` import into a directory with no dependency graph.
- **It owns its own `lit`.** This is subtle and load-bearing. After
  `npm install`, `react-app/node_modules/lit-component` is a symlink to this
  directory, and `react-app/node_modules/lit` does **not** exist. Vite/Rollup
  resolve a bare specifier relative to the *real* (symlink-resolved) path of the
  importing file — which is inside `lit-component/` — so `import 'lit'` in
  `Greetingcard.ts` resolves through `lit-component/node_modules/lit`. Adding
  `lit` to `react-app/package.json` instead would not work.

## Reproducing the generation

### 1. Install

```bash
cd examples/lit-in-react/lit-component
npm install
```

### 2. Generate the component

```bash
npm run generate
```

which is:

```bash
SWC_SRC=src SWC_PREFIX=demo- sirocco-wc add greetingcard
```

`sirocco-wc`'s config is `process.cwd()`-relative, so running it from this
directory with `SWC_SRC=src` targets `src/components/`. `SWC_PREFIX=demo-`
produces the `demo-greetingcard` tag name instead of the default `swc-`.

The `add` command already runs `buildCss` for you, so this one invocation
produces all five files:

```
src/components/index.ts                          # parent barrel (created/appended)
src/components/greetingcard/index.ts             # component barrel
src/components/greetingcard/Greetingcard.ts      # the component
src/components/greetingcard/Greetingcard.css     # Tailwind input (empty by design)
src/components/greetingcard/Greetingcard.styles.ts   # generated, gitignored
```

**Use a single-word component name.** `sirocco-wc add` derives the TypeScript
class name by upper-casing the first character of the argument
(`greetingcard` → `Greetingcard`). A hyphenated argument such as `greeting-card`
would yield `Greeting-card` — not a legal TypeScript identifier — and an equally
invalid `Greeting-cardStyle` export in the barrel, i.e. a hard syntax error.
The prefix is what makes the *tag* name hyphenated, which is all the custom
elements spec requires.

### 3. Hand-edit `Greetingcard.ts`

Two edits to the generated file:

**a. Fix the decorator import.** The generator emits an extensionless specifier:

```ts
import { customElement } from 'lit/decorators'   // ✗ as generated
```

`lit@3`'s `package.json` `exports` map has a `./decorators.js` key and no bare
`./decorators` key or wildcard, so under Vite/Rollup's strict ESM exports
resolution this throws `ERR_PACKAGE_PATH_NOT_EXPORTED`. Add the extension (this
is also the form used throughout sirocco-wc's own showcase template):

```ts
import { customElement, property } from 'lit/decorators.js'   // ✓
```

**b. Add the two properties and the event dispatch** the PoC needs — one
`@property({ type: String })`, one `@property({ type: Array })` to exercise
simple and complex prop passing, and a click handler dispatching a
`CustomEvent` with `bubbles: true, composed: true` so it escapes the shadow root.
See the final [`Greetingcard.ts`](./src/components/greetingcard/Greetingcard.ts);
the mechanics are explained in [../README.md](../README.md).

No `buildCss` re-run is needed after this edit. It introduces no new Tailwind
utility classes, so the generated CSS output is unchanged (verified: re-running
`npm run css:build` produces a byte-identical `Greetingcard.styles.ts`). **If you
add Tailwind classes to the template, re-run `npm run css:build`.**

## After a fresh clone: regenerate the styles

`*.styles.ts` is gitignored repo-wide (root `.gitignore` line 9), so
`Greetingcard.styles.ts` is generated output and is **not** committed. Run:

```bash
npm install
npm run css:build
```

Use `css:build`, **not** `generate`. `generate` re-runs the scaffolder, which
appends unconditionally and would leave a duplicate
`export * from './greetingcard/index';` line in `src/components/index.ts`.

Skipping this step fails `react-app`'s build with an error that names the missing
file outright:

```
[UNRESOLVED_IMPORT] Could not resolve './Greetingcard.styles' in ../lit-component/src/components/greetingcard/index.ts
```

## Type-checking in isolation

```bash
npm run typecheck
```

[`tsconfig.json`](./tsconfig.json) sets `experimentalDecorators: true` and
`useDefineForClassFields: false` for Lit's legacy decorators. Note that this file
is **not** what makes `react-app`'s build pass — `tsc -b` there type-checks one
whole program under `react-app`'s own options and pulls this source in
transitively, so those flags are repeated in `react-app/tsconfig.app.json`. See
[../README.md](../README.md) for the full explanation.
